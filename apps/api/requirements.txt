# Hard pins, matched to the versions already proven in the sibling projects.
# fastapi/starlette, PyJWT, cryptography and python-multipart were bumped
# in the hardening pass that added `pip-audit` to CI — each one had a real,
# fixed CVE (35 findings total; see HANDOFF.md's pass note). Re-verified:
# full test suite, mypy, and a live smoke test including a real multipart
# file upload through the upgraded python-multipart.
#
# sqlalchemy/asyncpg/alembic/psycopg2-binary/pydantic/pydantic-settings/
# structlog/argon2-cffi bumped in the dependency-upgrade sprint's low-risk
# batch (Sprint B) — no breaking changes in any of their release notes
# that touch how this project uses them (checked uvicorn's own
# setup_event_loop/reload_delay changes specifically since those move the
# most; this project never subclasses uvicorn.Config/Server, only invokes
# it via the CLI, so neither applies). redis stays pinned <6 here on
# purpose, not just conservatively — `arq` (this project's job queue,
# below) declares `redis[hiredis]<6,>=4.2.0` as a hard dependency, and
# arq is itself in maintenance-only mode with no newer release to lift
# that cap. Confirmed by actually trying `pip install redis==8.1.0`:
# pip's resolver reports the conflict outright. The Redis *server* was
# still bumped to 8 (infra/docker-compose.yml) — safe on its own since
# RESP3 is opt-in per-client, so this pinned RESP2 client is never
# forced onto it. Lifting this pin means replacing arq first (its own
# maintainers point to SAQ or Streaq), a real migration, not a version
# bump — tracked as its own future item, not silently deferred.
