# 02 — Data Model

**Scope reference:** [01_PRD.md](01_PRD.md) (requirements) · [03_API_SPEC.md](03_API_SPEC.md) (endpoints) · [04_SECURITY_AND_COMPLIANCE.md](04_SECURITY_AND_COMPLIANCE.md) (field protection, policies)

PostgreSQL 18 is the system of record. Nothing else holds durable state.

---

## 1. Conventions

### 1.1 Keys and identity

UUID v7 primary keys, generated by the **client** where the client needs to reference the row before the round-trip completes (cart items, lesson attempts, offline-capable writes), and by the server otherwise. UUID v7 is time-ordered, so it indexes like a sequence without leaking a row count the way `bigserial` does.

Never expose a sequential integer in a URL. The one deliberate exception is the invoice number, which *must* be sequential for SARS — and is therefore a separate column from the primary key, not the primary key itself (§6.4).

### 1.2 Base mixins

```python
class Base(DeclarativeBase):
    pass


class TimestampMixin:
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now(), nullable=False
    )
    updated_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now(), onupdate=func.now(), nullable=False
    )


class SoftDeleteMixin:
    deleted_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True), index=True)


class TenantMixin:
    """Every tenant-scoped table carries this. RLS policies key on it."""
    tenant_id: Mapped[UUID] = mapped_column(
        ForeignKey("tenants.id", ondelete="RESTRICT"), nullable=False, index=True
    )
```

All timestamps are `timestamptz`, stored in UTC. Naive datetimes are rejected by the `DTZ` ruff rules.

### 1.3 Tenancy

Shared database, shared schema, `tenant_id` on every scoped table, plus **PostgreSQL row-level security**. Application middleware sets `SET LOCAL app.tenant_id` at the start of each request transaction; RLS policies read it. Middleware alone is not enough — one forgotten `.filter()` in a reporting query is a cross-tenant leak, and RLS makes that a database error rather than a data breach.

Tables that are deliberately **not** tenant-scoped: `tenants`, `tenant_domains`, `roles`, `permissions`, and the global course catalogue rows that all tenants share. Tenant-specific catalogue visibility is a join table, not a copy.

### 1.4 Deletion

Soft delete for operational records. Hard delete only where privacy law requires it and financial retention allows it — which means a POPIA erasure request anonymises the learner and retains the invoice, because SARS retention outranks erasure for financial records. The erasure procedure is in [04 §5.3](04_SECURITY_AND_COMPLIANCE.md#53-data-subject-requests).

`ledger_entries` and `audit_events` support neither. See §1.5.

### 1.5 Append-only tables

`ledger_entries`, `audit_events`, `invoice_events` and `consent_records` are append-only, enforced in the database rather than by convention:

```sql
CREATE RULE ledger_entries_no_update AS ON UPDATE TO ledger_entries DO INSTEAD NOTHING;
CREATE RULE ledger_entries_no_delete AS ON DELETE TO ledger_entries DO INSTEAD NOTHING;
REVOKE UPDATE, DELETE ON ledger_entries FROM app_user;
```

A correction is a new compensating entry, never an edit. This is the mechanism behind the customer's "fully auditable for compliance" requirement.

### 1.6 Idempotency

Any table written from an external callback carries a unique idempotency key: `payment_webhooks.provider_event_id`, `meeting_events.provider_event_id`, `email_events.provider_message_id`. Replays are absorbed by a unique constraint, not by application logic.

### 1.7 Money

`NUMERIC(14, 2)` with a separate `currency CHAR(3)`. Never floats. Amounts are stored gross, net and tax as three explicit columns rather than derived, because recomputing historic VAT from a rate that has since changed is how audit trails break.

## 3. Enumerated types

Postgres native enums for closed sets that rarely change; lookup tables for anything an administrator configures.

```sql
CREATE TYPE order_status AS ENUM (
  'draft', 'pending_payment', 'eft_pending_proof', 'eft_pending_approval',
  'eft_rejected', 'po_pending_approval', 'paid', 'fulfilled', 'cancelled', 'refunded'
);

CREATE TYPE invoice_status AS ENUM (
  'draft', 'issued', 'partially_paid', 'paid', 'overdue',
  'cancelled', 'credited'
);

CREATE TYPE lesson_state AS ENUM (
  'locked', 'available', 'in_progress', 'requirements_met', 'completed'
);

CREATE TYPE attendance_status AS ENUM (
  'registered', 'joined', 'attended', 'partially_attended',
  'no_show', 'cancelled', 'rescheduled'
);

CREATE TYPE credential_status AS ENUM ('valid', 'expired', 'revoked');

CREATE TYPE survey_response_mode AS ENUM ('identified', 'anonymous');

CREATE TYPE manager_visibility AS ENUM ('aggregate_only', 'individual_enabled', 'disabled');

CREATE TYPE content_state AS ENUM ('draft', 'in_review', 'approved', 'published', 'archived');

CREATE TYPE access_level AS ENUM ('public', 'gated', 'guest', 'paid', 'corporate');
```

### 4.5 `organisations`, `organisation_members`

`organisations` holds the corporate customer: name, VAT number (encrypted), billing address (encrypted), payment terms, seat count. `organisation_members` joins users to organisations with a `relationship` column (`member`, `manager`, `admin`) — the manager relationship is an ABAC input, so it is a first-class row, not a role string.

### 4.6 `roles`, `permissions`, `role_permissions`, `role_assignments`

Permissions are strings (`course:publish`, `certificate:revoke`, `refund:process`). `role_assignments` is scoped: a user may be a Manager in one organisation and a Learner in another, so the assignment carries an optional `organisation_id` and `course_id`.

### 4.7 `entitlements`

The bridge between commerce and learning, and the reason tiering works without hard-coded package logic.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `tenant_id` | uuid FK | |
| `user_id` | uuid FK | Nullable — organisation-level entitlements exist before seat assignment |
| `organisation_id` | uuid FK | Nullable |
| `source_order_id` | uuid FK | Provenance. Never null in production data |
| `kind` | text | `course`, `learning_path`, `workshop_credit`, `coaching_credit`, `feature` |
| `target_id` | uuid | The course, path or feature key |
| `quantity` | integer | Credits remaining, where applicable |
| `granted_at` / `expires_at` | timestamptz | |
| `revoked_at` | timestamptz | Set on refund or chargeback |

### 4.8 `consent_records`

Append-only. One row per consent event: purpose (`marketing`, `analytics`, `ai_processing`), granted or withdrawn, timestamp, source, IP, and the exact policy version shown. A consent that cannot be evidenced did not happen.

### 4.9 `audit_events`

Append-only. `actor_user_id`, `actor_role`, `tenant_id`, `action`, `entity_type`, `entity_id`, `before`/`after` jsonb, `ip`, `user_agent`, `created_at`. Covers the event classes listed in [04 §8](04_SECURITY_AND_COMPLIANCE.md#8-audit-logging).

## 5. Catalogue and content

### 5.1 `courses`, `modules`, `lessons`

Standard hierarchy. `courses` carries `state content_state`, `manager_visibility`, the default `completion_rules` jsonb, `certificate_template_id`, `badge_template_id`, and CPD fields (nullable pending [01 §1.4](01_PRD.md#14-open-decisions-blocking-phase-0-sign-off) #7).

`lessons` carries `position`, `activity_type`, `access_level`, and its own `completion_rules` jsonb which overrides the course default when present.

### 5.2 `completion_rules` shape

Stored as jsonb, validated by a Pydantic model on write:

```json
{
  "minimum_time_seconds": 600,
  "video_watch_percentage": 80,
  "quiz_pass_score": 70,
  "quiz_max_attempts": 3,
  "survey_required": true,
  "assignment_approval_required": false,
  "live_attendance_required": false,
  "minimum_interval_seconds": 0
}
```

Every field is optional; an absent field means the rule does not apply. The engine evaluates the merged lesson-over-course rule set server-side on every progression request (REQ-BYPASS-01).

### 5.3 `course_tenant_assignments`

Which tenants may see which courses, and whether the course is bespoke to one tenant. A join table, never a duplicated course row — bespoke enterprise content is a visibility rule plus optional tenant-specific lessons.

### 5.4 `video_assets`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `source_object_key` | text | The uploaded master, in private storage |
| `duration_seconds` | integer | From `ffprobe` |
| `transcode_job_id` | uuid FK | |
| `playlist_object_key` | text | `master.m3u8` for the ladder |
| `renditions` | jsonb | Per rung: height, video kbps, maxrate, bufsize |
| `state` | text | `uploaded`, `transcoding`, `ready`, `failed` |

### 5.5 `transcode_jobs`

Mirrors the durable half of the ported `TranscodingEngine`: `state`, `progress_pct`, `processed_seconds`, `started_at`, `finished_at`, `error`, `retention_expires_at`. Progress is persisted at most every 5 seconds — FFmpeg emits `-progress` blocks roughly twice a second and every one of those does not need to be a database round-trip. On restart the worker hydrates from this table; the OS processes are gone, so no row carries a live handle.

### 5.6 `resources`, `podcast_episodes`

Marketing content. `access_level` decides gating (REQ-STORE-05). Podcast episodes carry transcript, show notes, and a `related_course_id` for the conversion CTA.

## 6. Commerce

### 6.1 `products`, `prices`

A product is sellable; a course is learnable. Separating them lets one course appear in several bundles at different prices. `prices` is per currency (`ZAR`, `USD`) with `tax_behaviour` (`inclusive`, `exclusive`) and validity dates. Prices are never edited — a change is a new row, so historic orders still resolve their original price.

### 6.2 `orders`, `order_items`

`orders.status` is the `order_status` enum from §3, driving the state machine in [01 §4.1](01_PRD.md#41-order-state-machine). Carries `currency`, `subtotal`, `tax_total`, `grand_total`, `po_number`, `po_document_key`, and `payment_reference` — the unique reference the learner quotes on an EFT.

Entitlements are created on the transition to `fulfilled`, in the same transaction.

### 6.3 `payments`, `payment_webhooks`, `refunds`

`payment_webhooks.provider_event_id` is unique, which is the whole idempotency mechanism (§1.6). Raw payloads are retained for reconciliation and stored encrypted, since they carry billing details.

`payments` records provider, provider reference, amount, currency, status, and for EFT the `proof_object_key`, `approved_by_user_id` and `approved_at`. **There is no auto-approval path for EFT.**

### 6.4 `invoices`, `invoice_items`, `credit_notes`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | Internal identity |
| `tenant_id` | uuid FK | |
| `number` | text unique per (tenant, series) | **The sequential, gapless number.** Never the primary key |
| `series` | text | Financial year or document class |
| `sequence` | integer | The integer behind `number` |
| `status` | invoice_status | |
| `issued_at` | timestamptz | |
| `currency`, `subtotal`, `tax_total`, `grand_total` | | |
| `exchange_rate` | numeric | Non-null when currency ≠ ZAR |
| `supplier_vat_number`, `customer_vat_number` | text | Snapshotted, not joined — the customer's VAT number may change after issue |

**Numbering.** Allocation happens inside the issuing transaction via a per-`(tenant_id, series)` counter row locked with `SELECT … FOR UPDATE`. Not a Postgres sequence: sequences are non-transactional and leave gaps on rollback, and a gap is exactly what SARS objects to. A failed issue rolls the counter back with the transaction.

An issued invoice is immutable. Correction means a credit note plus a new invoice.

### 6.5 `tax_rules`

Tax is data, not code. Each rule carries jurisdiction, customer type (individual, registered business, international), product class, rate, tax code and a human-readable reason. Every calculation writes the matched rule ID onto the invoice line, so an auditor can be shown *why* a line was zero-rated three years later.

South African VAT is 15% at the time of writing; it lives in a row, not a constant. International treatment is **blocked** pending [01 §1.4](01_PRD.md#14-open-decisions-blocking-phase-0-sign-off) #2.

### 6.6 `ledger_entries`

Append-only (§1.5). One row per financial event.

| Column | Type |
|---|---|
| `id`, `tenant_id` | uuid |
| `entity_type`, `entity_id` | text, uuid |
| `entry_type` | text — `invoice_issued`, `payment_received`, `refund_issued`, `credit_note_issued`, `write_off` |
| `amount`, `vat_amount`, `currency` | numeric, numeric, char(3) |
| `tax_code`, `reference` | text |
| `created_by`, `created_at` | uuid, timestamptz |
| `metadata` | jsonb |

### 6.7 `subscriptions`

Behind a feature flag pending [01 §1.4](01_PRD.md#14-open-decisions-blocking-phase-0-sign-off) #5. Plan, interval, seat count, current period, proration state, dunning attempts, gateway token reference. **No card data.**

## 7. Learning

### 7.1 `enrolments`

Joins a user to a course, sourced from an entitlement. Carries `started_at`, `completed_at`, `expires_at`, `cohort_id`.

### 7.2 `lesson_completions`

The authoritative progress record. `state lesson_state`, `first_seen_at`, `completed_at`, `accumulated_seconds`, and `rule_evaluation` jsonb — a snapshot of which requirements were met and which were not, at the moment of the decision. That snapshot is what makes a completion dispute resolvable.

### 7.3 `video_progress`

`furthest_position_seconds`, `watched_seconds`, `heartbeat_count`, `last_heartbeat_at`. `furthest_position_seconds` is the seek ceiling (REQ-BYPASS-04) and only ever increases. `watched_seconds` accumulates from validated heartbeats, so it cannot exceed wall-clock elapsed time — which is what makes a 0% → 100% jump impossible (REQ-BYPASS-03).

### 7.4 `video_heartbeats`

Append-only, partitioned monthly. `enrolment_id`, `lesson_id`, `position_seconds`, `playback_rate`, `session_id`, `created_at` — server-assigned. Client timestamps are discarded on arrival (REQ-BYPASS-02).

Retention: 90 days hot, then aggregated into `video_progress` and dropped. This is the highest-volume table in the system and the first partitioning candidate.

### 7.5 `quizzes`, `quiz_questions`, `quiz_attempts`, `quiz_answers`

Question banks with `randomise_questions` and `randomise_options` flags. `quiz_attempts` carries `attempt_number`, `started_at`, `submitted_at`, `score`, `passed`, and `invalidated_at` for suspected cheating — which triggers completion re-evaluation ([01 §4.4](01_PRD.md#44-re-evaluation-triggers)).

### 7.6 `surveys`, `survey_questions`, `survey_responses`

`surveys.response_mode` is the `survey_response_mode` enum, fixed at creation.

**When `anonymous`, `survey_responses.user_id` is not written.** Not nullable-and-empty — absent. The row carries `respondent_reference`, a random opaque token that lets the system reject duplicate submissions without knowing who submitted. A matching `audit_events` row proves anonymisation occurred at submission time, which is what makes the guarantee defensible later.

`surveys.minimum_group_size` (default 5) gates aggregate display.

### 7.7 `assignments`, `assignment_submissions`

Submissions carry `object_key`, `scanned_at`, `scan_result`, `version`, `reviewed_by_user_id`, `approved_at`. Files are virus-scanned before they are readable (REQ-BYPASS-08).

## 8. Credentials

### 8.1 `certificate_templates`, `certificates`

`certificates` carries `certificate_number` (public, opaque, unguessable — not sequential), `verification_token`, `issued_at`, `expires_at`, `status credential_status`, `revoked_reason`, `pdf_object_key`, and `snapshot` jsonb holding the learner name, course title and issuer as they were at issue. The snapshot matters: a learner who changes their surname does not invalidate a certificate already in circulation.

### 8.2 `badge_templates`, `badges`

Criteria, evidence URL, issuer metadata, level, `visibility` (`private`, `public`, `link_only`) chosen by the learner (REQ-CRED-07).

### 8.3 `credential_verifications`

Append-only log of public verification lookups: token, IP, user agent, result. Doubles as abuse detection on the verification endpoint.

## 9. Workshops

`facilitators`, `facilitator_availability`, `workshops`, `workshop_sessions`, `bookings`, `meeting_links`, `attendance_records`, `workshop_feedback`.

`meeting_links` abstracts the provider: `provider` (`teams`, `zoom`, `meet`, `manual`), `provider_meeting_id`, `join_url`, `organiser_user_id`. The manual provider is always available, which is what makes Graph API failures non-blocking.

`attendance_records.status` uses the `attendance_status` enum. `source` distinguishes `provider_report` from `facilitator_manual` — the facilitator can always override, whatever Graph says (REQ-WS-08).

## 10. CRM and marketing

`leads`, `contacts`, `deals`, `tasks`, `notes`, `activities`, `campaigns`, `segments`, `email_templates`, `email_sends`, `email_events`, `suppressions`.

`leads` carries the UTM quintet, `source`, `score`, `stage`, and the progressive-profiling fields from REQ-LEAD-02. Contact PII follows the same encryption pattern as `users` (§4.4).

`segments` store their criteria as jsonb over **non-PII attributes only** — tenant, package, lifecycle stage, course interest, UTM, consent flags, engagement counters. This is the resolution of the source material's unreconciled conflict between encrypted email and bulk marketing; the reasoning is in [04 §4.4](04_SECURITY_AND_COMPLIANCE.md#44-how-marketing-works-against-encrypted-email).

`suppressions` keys on `email_blind_index`, never plaintext, so suppression works without decrypting anything.

## 11. Analytics and AI

### 11.1 `events`

First-party, in Postgres (per [01 §5.11](01_PRD.md#511-analytics--first-party-in-postgres)). Partitioned monthly from the start — retrofitting partitioning on a hot table is painful.

```
id, tenant_id, anonymous_id, user_id (nullable), session_id,
event_name, event_properties jsonb,
utm_source, utm_medium, utm_campaign, utm_content, utm_term,
referrer, locale, country, device_type,
consent_marketing, consent_analytics,
created_at
```

`consent_*` are captured **on the row**, not looked up later. A consent withdrawal must not retroactively change what was lawfully collected, and it must not silently legitimise what was not.

### 11.2 `ai_jobs`, `ai_insights`, `ai_provider_configs`

`ai_jobs` records provider, model, prompt token count, completion token count, cost estimate, purpose, `consent_checked`, `redaction_applied`, and `identifiers_removed` — the count that makes the redaction claim auditable.

`ai_insights` links to a **cohort**, not a user, unless the course explicitly permits individual reporting (REQ-CRM-08). The foreign key reflects this: `cohort_id` is non-null, `user_id` is null except where a policy check has already passed.

Raw prompts are not retained by default. What is retained is the redaction log: input identifier count, output token map, and the sanitised prompt.

## 12. Cross-cutting

### 12.1 Retention

| Data | Retention |
|---|---|
| Video heartbeats | 90 days, then aggregated |
| Events | 24 months, then aggregated |
| Application logs | 30 days |
| Audit events | 7 years |
| Financial records | Per SARS requirement — outranks erasure requests |
| Guest accounts | Downgraded at expiry; lead record retained |
| AI job metadata | 24 months |

### 12.2 Seed data

An Alembic data migration seeds: the default tenant, the Phase 1 role and permission set, the South African VAT rule, a certificate template, and a break-glass administrator whose creation is **refused when the environment is production**. Demo content is a separate, explicitly-invoked seed script — never automatic.

### 12.3 Migration discipline

Every migration must round-trip: `upgrade head` → `downgrade -1` → `upgrade head`, enforced in CI. `alembic check` must report no model drift. Data migrations are separate revisions from schema migrations, so a schema rollback does not silently discard data.

Zero-downtime rule: add nullable, backfill, then constrain — never add a non-null column with a default to a large table in one step.

### 12.4 Scheduled integrity jobs

| Job | Cadence | Purpose |
|---|---|---|
| Guest expiry sweep | Hourly | Downgrade expired guests, retain the lead |
| EFT ageing alert | Daily | Flag approvals pending > 48 hours |
| Payment reconciliation | Daily | Gateway totals against ledger totals |
| Invoice sequence audit | Daily | Assert no gaps per tenant per series |
| Certificate expiry | Daily | Transition to `expired` |
| Heartbeat aggregation | Nightly | Roll up and prune |
| Restore drill | Quarterly | Manual, checklisted |

The invoice sequence audit is worth its own alert: a gap means something is wrong with the allocation transaction, and finding out from an auditor is not acceptable.

## 13. Open questions for engineering review

1. **UUID v7 generation** — Postgres 18 has `uuidv7()` natively; on 16 it comes from the application or an extension. Decide before the first migration, because changing it later rewrites every key.
2. **Events partitioning granularity** — monthly is proposed; weekly may suit if event volume exceeds projections.
3. **Blind index rotation** — rotating the HMAC key requires recomputing every index. Design the dual-index migration path before the first key is issued, not after.
4. **Bespoke enterprise lessons** — modelled as tenant-visible lessons inside a shared course. Confirm this survives a tenant wanting a wholly different module order.
5. **Cohort definition for AI insights** — minimum cohort size, and how cohorts are formed when an organisation has fewer members than the minimum.
6. **Video heartbeat interval** — 10 seconds is proposed. Shorter improves anti-bypass resolution and multiplies row volume.
