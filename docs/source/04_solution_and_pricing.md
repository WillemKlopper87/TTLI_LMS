# 1. Document Purpose

This document defines the technical solution for a multi-tenant executive training platform that includes:

- Course storefront and checkout
- Local and international payments
- Corporate invoicing / EFT / purchase orders
- LMS with anti-bypass completion controls
- Certificates and badges
- Live workshops using Microsoft Teams and other providers
- CRM / billing / marketing engine
- AI-assisted analytics using anonymized data
- White-label enterprise tenants
- Android/iOS ecosystem in later phases
- South African data residency requirements

The infrastructure approach is intentionally **lean**:

- Avoid Kubernetes at launch
- Avoid microservices at launch
- Avoid overprovisioned databases
- Avoid expensive always-on analytics clusters
- Use managed services where they reduce operational cost
- Use third-party services for hard problems: payments, email, DRM video, AI
- Scale only when measured usage triggers demand it

# 3. Core Technical Principles

## 3.1 Lean First

At launch, the platform should support:

- 50 to 500 active learners
- 100 concurrent users
- Marketing site
- Checkout
- LMS
- Admin/CRM
- Basic analytics
- Email notifications
- AI-assisted insights in controlled volumes

It does **not** need:

- Multi-region active-active
- Kubernetes
- Dedicated data warehouse
- Dedicated Redis cluster
- Dedicated search cluster
- Dedicated machine learning infrastructure
- Complex microservices

## 3.2 Modular Monolith

Use a modular monolith with clean domain boundaries.

Recommended modules:

- Identity and access
- Tenancy and white-labeling
- Catalog and content
- Commerce and billing
- Payments and tax
- LMS and progress
- Assessments and surveys
- Certificates and badges
- Workshops and scheduling
- CRM and marketing
- Analytics and events
- AI insights
- Notifications
- Admin and audit
- Integrations

This allows faster delivery and simpler operations while still permitting later extraction of high-load services.

## 3.3 Managed Services Over Self-Managed Servers

Prefer managed services for:

- PostgreSQL
- Object storage
- CDN
- Secrets
- Containers
- Monitoring
- Email delivery
- AI APIs
- DRM video delivery

Avoid managing:

- Video transcoding servers
- Email servers
- Search clusters
- Message brokers
- Redis clusters
- Kubernetes control planes

unless usage clearly demands it.

## 3.4 Cost Guardrails

Every environment must have:

- Budget alerts
- Autoscaling caps
- Log retention limits
- Backup retention limits
- Staging sleep schedules
- AI token caps
- Email volume caps
- Video streaming budget alerts

### Recommended Database Sizing

For 100 concurrent users:

- **Minimum lean:** B1ms, 1 vCore, 2 GB RAM
- **Recommended lean-safe:** B2ms, 2 vCore, 8 GB RAM
- Storage: 128 GB initially with autoscale storage enabled
- High availability: disabled initially to reduce cost
- Backups: automated daily + point-in-time restore
- Retention: 7 days initially, increase if compliance requires

If enterprise SLAs become critical:

- Enable zone-redundant HA
- Increase to D-series
- Add read replica for analytics/reporting

### Non-Production Environments

| Environment | Purpose | Cost Control |
|---|---|---|
| Local dev | Developer machines | Docker Compose, local Postgres, local storage emulator |
| Dev | Integration testing | Small container sizes, sleep outside working hours |
| Staging/UAT | Pre-production validation | Scaled-down production clone, sanitized data |
| Prod | Live platform | Autoscale caps, monitoring, alerts |

# 7. Multi-Tenant White-Label Architecture

## 7.1 Tenant Model

The platform must support multiple enterprise tenants.

Example:

- `acme.executivetrainingportal.co.za`
- `company1.executivetrainingportal.co.za`
- `clientx.executivetrainingportal.co.za`

Each tenant can have:

- Custom logo
- Custom primary/secondary colors
- Custom login background
- Custom support email
- Custom content catalog
- Custom registration fields
- Custom email branding
- Custom subdomain
- Optional SSO configuration
- Custom privacy rules
- Custom manager visibility settings

## 7.2 Tenant Resolution Flow

```text
Request arrives:
https://company1.executivetrainingportal.co.za/login

Reverse proxy / app resolves hostname
        |
        v
Tenant lookup by hostname
        |
        v
Tenant context loaded
        |
        v
Theme, content, entitlements, settings applied
```

## 7.3 Database Tenancy Strategy

Use a **shared database, shared schema** model with `tenant_id` on relevant tables.

Examples:

```text
users
tenant_id
organization_id
course_tenant_assignments
tenant_themes
tenant_sso_configs
tenant_content_rules
tenant_settings
```

For additional isolation:

- Use PostgreSQL Row-Level Security where practical
- Enforce tenant context in application middleware
- Log tenant context in audit logs
- For highly sensitive enterprise clients, consider dedicated schema later

## 7.4 Custom Domain Setup

For each enterprise tenant:

1. Create tenant record.
2. Generate CNAME target.
3. Customer configures DNS:
   - `company1.customerdomain.com`
   - or `company1.executivetrainingportal.co.za`
4. Platform validates domain.
5. TLS certificate provisioned automatically.
6. Tenant theme/content enabled.

# 8. Identity, Authentication, and Authorization

## 8.1 Authentication

### Core Authentication

- Email/password login
- Magic link login
- Password reset
- Argon2id password hashing
- TOTP MFA
- MFA required for admin/finance/facilitator roles

- Login audit logging

### Password Hashing

Use:

- Argon2id preferred
- Unique salt per password
- Strong memory/time parameters

Do not use:

- SHA-1
- Unsalted hashes

## 9.3 Encryption and Hashing Strategy

Important: not everything can be hashed. Some data must remain usable.

| Data Type | Protection Method |
|---|---|
| Passwords | Argon2id salted hash |
| MFA secrets | Encrypted with KMS/Key Vault |
| API tokens | Hashed or encrypted |
| Refresh tokens | Hashed |
| Email addresses | Encrypted + blind index for lookup |
| Phone numbers | Encrypted |
| Company name | Encrypted or pseudonymized for analytics |
| Billing address | Encrypted |
| VAT number | Encrypted or tokenized |
| Payment proof files | Encrypted object storage |
| Survey responses | Encrypted/pseudonymized |
| Assessment results | Role-restricted + encrypted where sensitive |
| Certificates | Public verification token, private generation metadata |
| Financial ledger | Immutable, encrypted at rest |
| Backups | Encrypted |
| Object storage | Encrypted at rest |

### Blind Index Example

For email lookup:

```text
email_encrypted = AES-GCM encrypted email
email_blind_index = HMAC-SHA256(lowercase_email, hmac_key)
```

The HMAC key is stored in Key Vault/KMS, not in the database.

## 9.4 Auditability for VAT and Compliance

The system must support:

- Sequential invoice numbering
- Immutable invoice events
- Credit note trail
- Tax calculation logs
- Payment source/reference
- Admin approvals
- EFT proof records
- Refund approvals
- Exportable tax reports
- Full audit trail of finance actions

Use an append-only ledger table:

```text

  id

  entity_type
  entity_id
  entry_type
  amount
  currency
  vat_amount
  tax_code
  reference
  created_by

```

Do not allow physical deletion of ledger entries.

# 13. LMS Architecture and Anti-Bypass Controls

## 13.1 Course Structure

```text
Course
  Module
    Lesson
      Video
      Document
      Quiz
      Survey
      Assignment
      Workshop requirement
```

## 13.2 Completion Rule Engine

Each lesson/course should have configurable rules.

Example:

```json
{
  "minimumTimeSeconds": 600,
  "videoWatchPercentage": 80,
  "quizPassScore": 70,
  "surveyRequired": true,
  "assignmentApprovalRequired": false,
  "liveWorkshopAttendanceRequired": false,
  "identityVerificationRequired": false
}
```

Completion decisions must be made server-side.

## 13.3 Anti-Bypass Controls

| Control | Purpose |
|---|---|
| Server-side lesson state | Prevent client manipulation |
| Video heartbeat events | Validate actual watching |
| Progress rate validation | Prevent jump to 100% |
| Signed playback tokens | Prevent unauthorized access |
| Quiz randomization | Reduce answer sharing |
| Attempt limits | Prevent brute-force guessing |
| Time limits | Enforce assessment integrity |
| Survey submission lock | Prevent duplicate responses |
| Assignment approval workflow | Validate human-reviewed work |
| Concurrent session limits | Reduce account sharing |
| Audit logs | Detect suspicious behavior |

## 13.4 Survey Anonymity

Each survey has a setting:

```text
response_mode = identified | anonymous
```

If anonymous:

- Do not store user_id with response
- Store random respondent_reference
- Prevent manager-level individual reporting
- Allow aggregate analytics only
- Retain audit proof that response was anonymized at submission

## 13.5 Manager Visibility Controls

Course-level settings:

```text
manager_visibility = aggregate_only | individual_enabled | disabled
```

Tenant-level setting:

```text
allow_manager_individual_results = true/false
```

System administrator can override per course where justified.

Default recommendation:

- Managers see:
  - Completion percentage
  - Number of learners completed
  - Aggregate assessment trend
  - Participation rate
- Managers do not see:
  - Individual quiz scores
  - Individual survey answers
  - Individual weakness analysis

unless explicitly enabled.

# 18. AI Architecture and Anonymization

## 18.1 AI Provider Strategy

Support top providers through an abstraction layer:

| Provider | Notes |
|---|---|
| OpenAI | Strong general reasoning |
| Anthropic Claude | Strong long-context and writing |
| Google Gemini | Useful if Google ecosystem is adopted |
| Microsoft Copilot / Azure OpenAI | Strong enterprise/Microsoft alignment |

Primary recommendation for enterprise Microsoft environment:

- Use Azure OpenAI where procurement/compliance allows
- Use Microsoft Copilot integrations later where applicable

Important: verify current AI data residency availability. If AI provider does not process prompts in South Africa, ensure:

- Data is anonymized before transmission
- Legal/DPA review is completed
- No direct personal identifiers are sent
- Customer policy allows cross-border anonymized processing

## 18.2 Anonymization Pipeline

Before sending data to AI:

1. Extract assessment/survey/feedback text.
2. Remove direct identifiers:
   - Names
   - Emails
   - Phone numbers
   - Company names
   - Tenant names
   - ID numbers
   - Locations that can identify a person
3. Replace with tokens:
   - `[PERSON_1]`
   - `[COMPANY_1]`
   - `[DATE_1]`
4. Remove or hash user IDs.
5. Send sanitized prompt to AI provider.
6. Store insight, not raw prompt, where possible.
7. Record AI job metadata:
   - Provider
   - Model
   - Token usage
   - Cost estimate
   - Purpose
   - Consent check
   - Anonymization status

## 18.3 AI Use Cases

- Survey theme extraction
- Sentiment analysis
- Skill gap identification
- Course drop-off insights
- Leadership assessment summaries
- Learner risk scoring
- Executive summary generation
- Content recommendations

## 18.4 AI Guardrails

- Token budget per tenant/month
- Human review for important insights
- No automated disciplinary or punitive actions
- No processing of anonymous survey data in identifiable form
- Prompt injection protection
- Output validation
- Fallback provider
- Disable AI per tenant

# 5. Suggested Commercial Terms

## 5.1 VAT and Tax

- South African prices may be displayed exclusive or inclusive of VAT, but must be clearly labeled.
- International USD pricing should state whether taxes are excluded.
- Invoices must include VAT registration details where applicable.
- Tax treatment must be validated by accountants.

## 5.2 Payment Terms

| Customer Type | Payment Terms |
|---|---|
| Individual | Immediate card/payment gateway |
| Corporate | Invoice, EFT, PO, 15/30-day terms |
| Enterprise | Custom contract terms |

## 5.3 Refund Policy

Suggested:

- 7-day refund for individual digital purchase if less than 20% completed, optional
- Corporate packages subject to contract
- Live workshops subject to cancellation policy
- One-on-one sessions require 48-hour notice

## 5.4 Subscription Terms

If subscriptions are used:

- Monthly/annual billing
- Auto-renewal clearly disclosed
- Proration on upgrades
- Downgrades effective next cycle
- Failed payments trigger grace period
- Cancellation stops future billing but may retain access until period end

## 5.5 Corporate Seat Terms

- Seats are assigned, not shared
- Unused seats may not be refunded unless contract allows
- Seat reassignment allowed
- Minimum seat count may apply

## 5.6 Enterprise Terms

Enterprise agreements should cover:

- Tenant isolation
- SSO configuration
- Data retention
- Support SLA
- Uptime target
- Security review rights
- Subprocessor list
- AI data handling
- Content ownership
- Custom development
- Termination and export

# 7. Final Recommendation

For the technical build:

- Start with a **lean modular monolith**
- Use **managed PostgreSQL**
- Use **PostgreSQL-based job queue** before Redis
- Use **external DRM video provider**
- Use **external email/AI/payment providers**
- Deploy in **South Africa region**
- Avoid Kubernetes and microservices initially
- Add scaling components only when metrics justify them

For commercial packaging:

- Start with **Free/Guest**, **Individual**, **Team**, and **Enterprise White-Label**
- Use add-ons for live sessions, coaching, SSO, AI analytics, and custom development
- Keep enterprise pricing flexible and quote-based
- Make VAT, PO/invoice, and auditability core selling points

This gives the customer a credible, enterprise-ready platform without inflating early infrastructure costs.
