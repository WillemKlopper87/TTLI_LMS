# 1. Recommended Overall Approach

## 1.1 What you are really building

This is not just a website. It is a combined:

1. **E-commerce / course storefront**
2. **Payment and billing platform**
3. **LMS / learning experience platform**
4. **Live workshop and scheduling system**
5. **Certification and digital badge engine**
6. **CRM and marketing automation system**
7. **Analytics and AI insights platform**
8. **Multi-tenant B2B/B2C training portal**

Because the scope may change, I would recommend building this as a **modular monolith first**, with clear domain boundaries, rather than starting with a complex microservices architecture.

A modular monolith gives you:

- Faster delivery
- Easier debugging
- Lower infrastructure cost
- Simpler transaction handling
- Easier refactoring later if specific services need to scale independently

You can later extract high-load services such as analytics, notifications, AI processing, or video processing if required.

## 4.2 Checkout, Payments, and EFT

This is a critical area. It needs to be reliable, auditable, and secure.

### Payment Methods

#### 1. Payfast

Use Payfast for card payments and supported South African payment methods.

Recommended integration:

- Use Payfast hosted checkout or secure redirect.
- Do not store card details on your system.
- Validate IPN/webhook notifications.
- Use sandbox environment during development.
- Handle:
  - Pending
  - Paid
  - Failed
  - Cancelled
  - Refunded
  - Chargeback, if applicable

#### 2. Netcash

Use Netcash for card/EFT or other supported local payment options.

Recommended integration:

- Use hosted/redirect payment flow where possible.
- Validate webhook/callback notifications.
- Use reference numbers.
- Handle asynchronous payment updates.
- Reconcile payment status carefully.

#### 3. Direct EFT Deposit

This is common for corporate customers.

Required features:

- Display bank account details at checkout.
- Generate a unique payment reference.
- Allow user to upload proof of payment.
- Send notification to finance/admin.
- Admin approves/rejects payment.
- Enrollment is activated only after approval.
- Optional: bank statement import/reconciliation.
- Optional: integration with bank APIs if available.

Direct EFT should be treated as a manual payment workflow.

### EFT Workflow

1. Customer selects “Direct EFT”.
2. Order is created with status: `Pending Payment`.
3. System displays banking details and payment reference.
4. Customer uploads proof of payment.
5. Finance/admin reviews proof.
6. Admin marks payment as:
   - Approved
   - Rejected
   - Requires correction
7. If approved:
   - Order becomes `Paid`
   - Enrollment is created
   - Login credentials/onboarding email are sent
8. If rejected:
   - Customer is notified
   - Enrollment remains inactive

## 4.5 Anti-Bypass Controls

This is one of the most important requirements. The system must not allow users to simply click “Next” or mark lessons complete without actually engaging.

The key rule is:

> The frontend can show progress, but the backend must be the source of truth.

Never trust the browser/client to decide completion.

### Completion Rule Engine

Each course/module/lesson should have configurable completion rules.

Example completion criteria:

```json
{
  "minimumTimeSeconds": 600,
  "videoWatchPercentage": 80,
  "quizPassScore": 70,
  "surveyRequired": true,
  "assignmentApproved": false,
  "liveAttendanceRequired": false,
  "identityVerificationRequired": false,
  "minimumIntervalBetweenLessons": true
}
```

A lesson/course is completed only when all required criteria are satisfied.

### Controls to Prevent Bypassing

| Risk | Control |
|---|---|
| User clicks “Next” repeatedly | Server-side validation; API rejects progression unless criteria met |
| User marks video complete without watching | Signed video progress events, watch percentage, heartbeat, maximum progress rate |
| User fast-forwards video | Prevent jumping beyond allowed progress; use streaming player events; anomaly detection |
| User guesses quiz answers | Randomized questions, attempt limits, time limits, question bank |
| User submits empty assignment | Required fields, file type validation, facilitator approval |
| User skips survey | Survey required before course completion |
| User shares account | Concurrent session limits, device/session tracking, optional one-time login codes |
| User manipulates frontend | All completion decisions happen server-side |
| User bypasses prerequisites | Prerequisite engine enforced in backend |
| User manipulates timestamps | Server-side timestamps only; client timestamps ignored |
| User leaves page open | Heartbeat/activity validation, not just time on page |
| User manipulates API | Authentication, authorization, rate limiting, signed events, audit logs |

### Video Progress Controls

For video lessons:

- Use a secure video player.
- Use signed URLs or signed cookies.
- Store progress server-side.
- Send periodic heartbeat events.
- Validate that progress increases at a realistic rate.
- Do not allow progress to jump from 0% to 100% instantly.
- Require minimum watch percentage.
- Optionally prevent downloading.
- Optionally watermark the player with user email or ID.
- Optionally use DRM for high-value content.

### Quiz Controls

- Question banks
- Randomized question order
- Randomized answer order
- Time limits
- Attempt limits
- Passing score
- Review policy:
  - Show correct answers after pass, or
  - Hide correct answers to prevent memorization
- Anti-cheating flags:
  - Multiple attempts from same IP
  - Unusually fast completion
  - Copy/paste detection, optional
- Manual grading for open-ended responses

### Survey Controls

- Required surveys can block completion.
- Anonymous surveys can be supported.
- For analytics, allow opt-in where needed.
- Prevent duplicate submissions.
- Allow editing only where appropriate.
- Store consent for processing responses.

### Assignment Controls

- File upload restrictions
- Virus scanning
- Submission timestamps
- Versioning
- Facilitator review
- Approval/rejection workflow
- Feedback comments
- Resubmission rules

### Live Workshop Attendance Controls

For live sessions, completion may depend on attendance.

Controls:

- Unique join link per learner
- Authenticated access to workshop page
- Facilitator marks attendance
- Optional automatic attendance from Zoom/Teams/Meet reports
- Attendance status:
  - Registered
  - Joined
  - Attended
  - Partially attended
  - No-show
  - Cancelled
  - Rescheduled
- Minimum attendance duration
- Post-workshop survey required
- Facilitator approval required, optional

### Important Note

No system can completely prevent a determined malicious user, but you can create strong technical and process controls that make bypassing difficult, detectable, and auditable.

# 5. RBAC and ABAC

## 5.1 RBAC: Role-Based Access Control

RBAC assigns permissions based on role.

### Suggested Roles

| Role | Description |
|---|---|
| Visitor | Can browse public pages |
| Learner | Can access purchased training |
| Corporate Learner | Learner belonging to an organization |
| Team Manager | Can view reports for team members |
| Organization Admin | Manages learners, seats, billing for a company |
| Facilitator | Runs live workshops, marks attendance, gives feedback |
| Content Author | Creates/edits courses |
- Content Reviewer | Reviews/approves content |
| Finance | Manages payments/invoices/refunds |
| Marketing | Manages campaigns/newsletters/CRM |
| Support | Handles learner support and limited admin actions |
| Analyst | Views analytics but cannot change operational data |
| Administrator | Broad administrative access |
| Super Admin | Full system access |
| Auditor | Read-only audit/analytics access |

### Example Permissions

- `course:view`
- `course:edit`
- `course:publish`
- `lesson:complete`
- `quiz:grade`
- `assignment:review`
- `workshop:create`
- `workshop:attendance:mark`

- `refund:process`
- `user:invite`
- `user:suspend`

## 5.2 ABAC: Attribute-Based Access Control

ABAC allows more dynamic policies.

Attributes may include:

- User role
- User organization
- User package tier
- Enrollment status
- Payment status
- Course ownership
- Lesson publication status
- Workshop date
- Manager relationship
- Consent status
- Data sensitivity
- IP address
- Device/session trust
- Time of day

### Example ABAC Policies

#### Policy 1: Lesson access

Allow access to a lesson only if:

- User is authenticated
- User has active enrollment
- Payment is complete
- Course is published
- User’s package includes the course
- Lesson is published
- Prerequisites are complete

#### Policy 2: Manager reporting

A manager can view learner analytics only if:

- Manager and learner belong to same organization
- Learner has consented to manager reporting, if required
- Manager role includes `team:reports:view`
- Data is limited to aggregate/permitted fields

#### Policy 3: Finance access

Finance user can view invoices only if:

- User has finance role
- Organization matches, for multi-tenant finance
- Resource is not restricted by legal hold

#### Policy 4: AI analytics access

AI analytics can process survey/test data only if:

- User consent allows processing
- Data is pseudonymized
- Organization has AI analytics enabled
- Sensitive fields are excluded

### Recommended Policy Engine

Use one of:

- Open Policy Agent, OPA
- Casbin
- Custom policy engine with strict tests

Do not scatter permission checks randomly through the code. Centralize authorization logic.

## 6.4 AI Guardrails

Very important.

AI integration should include:

- Provider abstraction layer
- API key stored in secrets manager
- Token/cost budget
- Rate limiting
- Prompt templates
- Data minimization
- PII redaction
- Anonymization/pseudonymization
- Consent checks
- Human review for important decisions
- Audit logs of AI requests, without storing sensitive prompts unnecessarily
- No automatic high-impact decisions without human approval
- Model output disclaimer
- Evaluation/testing of prompts
- Protection against prompt injection
- Option to disable AI per tenant
- Option for customer to bring their own AI key

### Example AI Analytics Flow

1. Learner completes assessment/survey.
2. Event is stored in database.
3. Data is queued for analytics processing.
4. PII is removed or pseudonymized.
5. AI provider analyzes text/answers.
6. Result is stored as insight:
   - Sentiment
   - Theme
   - Risk score
   - Recommendation
7. Admin dashboard displays insight.
8. Human can review/override.

# 11. Security Requirements

This platform will handle payments, personal data, corporate training data, and possibly sensitive executive assessments. Security must be treated as a first-class requirement.

---

## 11.1 Application Security

### Secure Coding Practices

- Input validation on all endpoints
- Output encoding
- Parameterized queries
- CSRF protection
- XSS protection
- Secure HTTP headers:
  - HSTS
  - CSP
  - X-Content-Type-Options
  - X-Frame-Options
  - Referrer-Policy
- Rate limiting
- Brute-force protection
- Secure session management
- Secure cookie flags:
  - HttpOnly
  - Secure
  - SameSite
- File upload validation
- Virus scanning for uploads
- Secrets never stored in code
- Dependency scanning
- Logging without sensitive data

### OWASP Compliance

Target alignment with:

- OWASP Top 10
- OWASP ASVS, where practical
- OWASP LLM Top 10, if AI features are exposed

---

## 11.2 Authentication Security

- Strong password policy
- Password hashing with Argon2 or bcrypt
- MFA for privileged roles
- Password reset tokens with expiry
- Magic link tokens with expiry
- Session timeout
- Concurrent session controls
- Login anomaly detection
- Account lockout or progressive delay
- Audit login attempts
- Optional SSO for enterprise

---

## 11.3 Authorization Security

- Centralized RBAC/ABAC
- Least privilege
- Resource-level checks
- Tenant isolation
- Prevent horizontal privilege escalation
- Prevent vertical privilege escalation
- Policy tests
- Audit permission changes
- Admin actions require elevated permissions

---

## 11.4 Payment Security

- Do not store card data
- Use hosted checkout/redirect where possible
- Validate webhooks/signatures
- Idempotent webhook processing
- Reconcile gateway status with database
- Log payment events
- Prevent duplicate enrollments
- Prevent order tampering
- Use HTTPS only
- PCI DSS scope reduction, ideally SAQ A or SAQ A-EP depending on integration
- Fraud checks:
  - Velocity rules
  - Suspicious email domains
  - Duplicate accounts
  - High-risk transactions
- Refund approval workflow
- Finance audit trail

# 21. Final Recommendation

The best approach is to build a **modular, cloud-native training commerce and LMS platform** with:

- A secure storefront and checkout
- Payfast/Netcash/EFT payment handling
- A server-authoritative LMS completion engine
- Strong RBAC/ABAC entitlement controls
- Certificates and verifiable badges
- LinkedIn-friendly achievement sharing
- Live workshop scheduling with Zoom/Teams/Meet
- Corporate/group training support
- Billing/invoicing/CRM
- Bulk email/newsletter capability
- AI-assisted analytics with strict privacy controls

The most important design principle is:

> Completion, certification, payment, entitlements, and analytics must all be controlled and validated server-side. The frontend should only provide the user experience, not enforce business rules.

Start with a modular monolith, deploy to AWS or Azure using managed services, and phase the delivery so the customer can launch an MVP and then expand into advanced corporate, AI, and enterprise features.
